# ADR 0004 — M4 the gate: the return type that excludes the human-authorized halt mode, the `agent` parameter's real job, the `ResourceClaimId` ruling, and why a text scan is the right tool here

- **Date:** 2026-09-22
- **Status:** accepted
- **Phase / milestone:** M4 (BUILD) — `lib/gate/**`

## Context

`.genesis/PLAN.md` §4's M4 entry scopes this milestone to `availableInterventions(agent, claim,
checkpoint, now): Set<Intervention["kind"]>` (with halt's two modes distinguished) — computed from
`Corroboration` and checkpoint freshness alone, independent of severity (M5's job). `lib/contracts/**`
(M1) and `lib/conflict/**` (M3) are both frozen/settled inputs to this milestone; this milestone's own
scope is `lib/gate/**` and this file. This milestone inherits two obligations stated, but not yet
checkable, by earlier milestones: M1's central design commitment, relocated here by
`.genesis/decisions/0001-contracts.md` Decision 2 ("no module under `lib/` ever mints a `HumanId`, or
assembles [the human-authorized halt mode's] `Intervention` from scratch" — with M4's own version of
the check already named, verbatim, in the plan itself), and `0001-contracts.md` Decision 3's open
question about whether `ResourceClaim` needs an `id` field for `quarantine`'s sake, left open pending "a
real consumer."

Four things had to be resolved before a single line of gating logic could be written, none solvable by
silently picking an answer.

## Decision 1 — `AvailableInterventionKind`: a new, derived union, not the plan's literal `Intervention["kind"]`, and why the departure is required, not a shortcut

`.genesis/PLAN.md` §4 M4's own scope line states the return type as `Set<Intervention["kind"]>` and,
in the same sentence, requires "halt's two modes distinguished." These two requirements are mutually
exclusive as written: `Intervention["kind"]` (`lib/contracts/intervention.ts`) is a bare 5-member
union — `"observe" | "warn" | "pause" | "halt" | "quarantine"` — with no way to tell which of
`Intervention`'s two `halt` modes a `"halt"` string refers to; `mode` is a separate field that exists
only once a full `Intervention` object (not just its `kind`) is in hand. A `Set<Intervention["kind"]>`
literally cannot distinguish the two halt modes at all. This is the identical shape
`.genesis/decisions/0001-contracts.md` Decision 3 already named for `Conflict`/`ResourceClaim`'s
missing `id` fields: "two places in the plan pull in different directions," resolved there by building
the richer shape the stated requirement actually needs, documented here rather than silently guessed.

**Chosen:** `lib/gate/available-interventions.ts` defines
`AvailableInterventionKind = Exclude<Intervention["kind"], "halt"> | "halt-checkpointed"`. Four of five
members (`observe`, `warn`, `pause`, `quarantine`) are mechanically tied to `Intervention["kind"]`'s own
frozen union via `Exclude`, so this file cannot silently drift out of sync with `lib/contracts` for
those four. `"halt"` is removed from that projection in full, and exactly one new, hand-written literal
— `"halt-checkpointed"` — is added back, naming only the checkpoint-anchored halt mode. This
satisfies the plan's own parenthetical (the two modes ARE distinguished — one has its own named
literal, the other has none at all) while making the intended return type buildable at all.

**This is the actual mechanism this milestone's central commitment rests on, not incidental to it:**
there is no third, halt-shaped member in this union. The human-authorized halt mode has no string
literal anywhere in `AvailableInterventionKind`, no field on any of its five members that could carry
one, and `availableInterventions` itself never constructs an `Intervention` object at all — it builds
a `Set` of plain string labels. This is checked at the type level by four `@ts-expect-error` tests in
`__tests__/available-interventions.test.ts` (assigning that mode's own literal, or the bare `"halt"`
literal, to `AvailableInterventionKind` must not compile; constructing a `Set<AvailableInterventionKind>`
containing that literal must not compile without a cast) and independently reconfirmed by a source-scan
test — see Decision 6.

**Alternative considered and rejected: return the plan's literal `Set<Intervention["kind"]>` and
accept that halt's two modes cannot be distinguished this milestone.** Rejected — the plan's own
parenthetical is not decorative; `.genesis/DONE.html`'s locked M1 gate already requires `pause`/`halt`
checkpointed literals to require a `checkpointId`, and this milestone's own falsifiability check
(boundary test) is specifically about the checkpoint-anchored halt mode's availability, which a
mode-blind `"halt"` string could not express independently of `pause`.

**Alternative considered and rejected: hand-write all five literals independently, with no structural
tie to `Intervention["kind"]` at all.** Rejected — this would let `AvailableInterventionKind` drift
silently from `lib/contracts/intervention.ts`'s own frozen spelling (a typo in one of the four
unchanged names would be a second, independent bug to catch, not a type error against the real
source of truth). Deriving four of five members mechanically costs nothing and removes that whole
class of drift.

## Decision 2 — the `agent` parameter's real job: a claim/agent identity consistency check, failing closed to the observe/warn baseline, not a third independent gating axis

`.genesis/PLAN.md` §4 M4's own scope line names `agent` as this function's first parameter, and
`tsconfig.lib.json`'s `noUnusedParameters` makes an unread parameter a build error, not merely a lint
suggestion — so `agent` had to be given a real, non-decorative job, not left referenced only to satisfy
the compiler.

**Chosen:** `claim` already carries its own `agentId` (`lib/contracts/resource-claim.ts`, frozen).
`availableInterventions` compares `claim.agentId` against the `agent` parameter; on a mismatch, it
returns the `observe`/`warn` baseline only, regardless of what `claim.corroboration` or `checkpoint`
would otherwise permit. This is argued, not merely convenient: this project's own thesis (plan §1) is
that the tower acts "using only what th[e] process chooses to report about itself" — which presumes
the report being read and the process being acted on are the same one. A caller that hands
`availableInterventions` a claim belonging to one agent while asking about a different one has
supplied an internally inconsistent input, and this milestone treats that the same way this codebase
treats every other input it cannot make sense of: fail closed to the weakest defensible answer, never
guess which of the two identities is authoritative, never throw (matching the typed-result style
`lib/contracts/intervention.ts` and `lib/conflict/detection-result.ts` already use elsewhere, adapted
here to a case where the "smaller than it could have been" `Set` already expresses the refusal without
a separate error shape).

**The tension with the plan's own wording, named directly rather than silently resolved:** plan §4 M4
says availability is "computed from `Corroboration` and checkpoint freshness alone" — a phrase that
could be read to forbid this check as a third gating input. This ADR reads "alone" as scoping which
DATA SOURCES may ever ADD permission beyond the baseline (only corroboration and freshness ever do,
confirmed by `__tests__/available-interventions.test.ts`'s own "the two gating axes are independent"
describe block), not as forbidding a consistency check on the two identities the signature's own
parameters already carry. The agent-mismatch path never grants anything a matching agent would not
already get; it only ever withholds. Recorded here explicitly, per this account's own standing practice
of not silently resolving a plan ambiguity, so a reader who takes "alone" the other way can see the
call was made, and why.

**Alternative considered and rejected: prefix the parameter `_agent` and leave it genuinely unread,
deferring any identity check to a later milestone.** Considered seriously, since this project's own
`0001-contracts.md` Decision 5/`0003-detection.md` Decision 4 repeatedly warn against inventing an
unrequested check. Rejected because this specific check is not speculative — it directly follows from
the signature already carrying two overlapping pieces of identity information, and this project's own
central thesis is precisely about not letting a report about one process be mistaken for another's.
Leaving it structurally inert would also read as evasive under review: a parameter present in the
signature but never consulted for anything is exactly the kind of decorative compliance this account's
own ADRs elsewhere refuse to accept from itself.

## Decision 3 — the `ResourceClaimId` question: ruled OPEN, not closed, despite `quarantine` appearing in this milestone's own output

`.genesis/decisions/0001-contracts.md` Decision 3 left `ResourceClaim` with no `id` field while
`Intervention.quarantine` requires `NonEmptyArray<ResourceClaimId>`, reasoning that only a milestone
with "a real consumer" could verify the right shape. This milestone's own task names `quarantine` as
part of its output set and frames this milestone as that first real consumer. Read closely against
what this milestone's own function actually does, the ruling is: **it is not.**

**The argument:** `availableInterventions` returns `AvailableInterventionKind` — a bare string label,
`"quarantine"` — never an `Intervention` value. This milestone's own task statement draws the line
precisely where this argument needs it drawn: "It does not choose one — that is M5's arbitration. It
bounds the set." Naming which SPECIFIC claim(s) a quarantine would revoke is not a fact about whether
quarantine is structurally PERMITTED at all (this function's only question) — it is content that exists
only once a caller actually ASSEMBLES a `{ kind: "quarantine", revokedClaims: NonEmptyArray<
ResourceClaimId> }` value, which is `arbitrate`'s (M5, unbuilt) job by the plan's own division of labor,
not this gate's. `availableInterventions` never needs to look a claim up by id — it is handed the
claim object directly, already whole, and reads exactly one field off it (`corroboration`); the caller
that passed the claim in already has whatever reference it needs to correlate this function's boolean-
shaped answer ("is quarantine available for this claim") back to the claim it asked about, with no id
required on `ResourceClaim` itself for that correlation to work.

**Directly addressing the counter-reading:** one could argue that "quarantine is available" is a
close-to-meaningless answer without also saying "revoking WHICH claim," since the entire content of
that `Intervention` variant IS the revocation list. This ADR does not dismiss that reading, but resolves
it: it correctly describes what a downstream RULING should eventually be able to say, not what THIS
milestone's own named signature commits to returning. `.genesis/PLAN.md` §4 M4's own literal scope line
types the return as `Set<Intervention["kind"]>` — kinds, not values — and this ADR treats that literal
signature as authoritative over the higher-level §3 pipeline label ("`AvailableInterventionSet` per
agent, per conflict"), the same way Decision 1 above treats it as authoritative over the plan's
underspecified mode-blindness. A milestone that returns kind-level availability is a real, useful, and
narrower thing than a milestone that constructs values — and this one is the narrower thing.

**Chosen:** the `ResourceClaimId`-identifies-a-claim gap `0001-contracts.md` Decision 3 named stays
open, for M5 (`arbitrate`) to close against its own real code — the first milestone that actually
constructs a `quarantine` `Intervention` value and therefore the first that must know which claim(s) a
revocation names. This milestone is a real, new consumer of `Corroboration` (a field, not an id) and of
`AvailableInterventionKind` (`"quarantine"` as a label); it is not a real consumer of `ResourceClaimId`
as an identity a claim carries, and does not pretend otherwise for the sake of matching this task's own
framing.

**Consequence, stated for M5 to inherit deliberately, and at its true weight rather than understated as
merely "left open":** `arbitrate` will need SOME way to correlate "the claim `availableInterventions` was
asked about" with "the id to put in `revokedClaims`" once it starts calling this gate for real,
multi-claim conflicts — and, checked directly rather than assumed, **nothing in the pipeline built so far
carries per-claim identity at all.** `ResourceClaim` (frozen, M1) has no `id` field.
`DetectedConflict` (`lib/conflict/detected-conflict.ts`, M3) carries a `NonEmptyArray<AgentId>` for its
participants, not a `NonEmptyArray<ResourceClaimId>` — it identifies WHO collided, never WHICH of their
claims. `AvailableInterventionSet` (this milestone) is keyed by nothing at all; a caller correlates it
back to the claim it passed in only by holding its own reference, not by any id this pipeline hands back.
And `.genesis/PLAN.md` §4 M5's own literal signature — `arbitrate(conflicts: Conflict[], available:
AvailableInterventionSet[], severity: ConflictSeverity, humanAuthorization?: HumanAuthorization):
InterventionRuling[]` — has **no claims parameter at all**, only conflicts and availability sets. This
means M5 cannot close this gap by simply "adding an id field" in isolation: it will need either a
`lib/contracts` unfreeze (adding `id: ResourceClaimId` to `ResourceClaim` — a real, deliberate reopening
of a boundary five verification rounds already hardened) or a signature departure from the plan's own
literal M5 text (e.g., an `arbitrate` parameter carrying claims alongside conflicts, the same class of
"the plan's prose and its own later requirement pull in different directions" departure this milestone
made for its own signature in Decision 1, and `lib/conflict/detect-conflicts.ts` made for M3's). Either
path is a bigger cost than "left open" by itself conveys, and either has real precedent already in this
codebase: `0001-contracts.md` Decision 3 for the unfreeze-shaped option, `lib/conflict/detected-
conflict.ts`'s own `DetectedConflict` wrapper (Decision 2 of `0003-detection.md`) for the
signature-departure-shaped one. Recorded here at this weight specifically so M5's builder budgets for a
real design decision, not a one-line addition.

## Decision 4 — what this milestone reads from `ResourceClaim`/`CheckpointDeclaration`, and what it deliberately never reads

Plan §4 M4's own scope line: availability is "computed from `Corroboration` and checkpoint freshness
**alone**." Taken at that strength, this function reads exactly two facts — `claim.corroboration` and
`(checkpoint.reachable, checkpoint.declaredAt)` compared against `now` — plus, per Decision 2,
`claim.agentId` for the identity consistency check. Four fields this milestone's inputs carry are read
nowhere in this function, each deliberately, not by oversight:

- **`claim.declaredAt`** — order-independence for detection is `lib/conflict/**`'s own settled
  concern (`0003-detection.md` Decision 4); this function does not detect anything, and has no
  ordering question of its own to ask about when a CLAIM was made.
- **`claim.ttl`** — `0001-contracts.md` Decision 5 already named this milestone (`availableInterventions`,
  then unbuilt) as the one that would decide what, if anything, `ttl` staleness means, and
  `0003-detection.md`'s own Decision 4 consequence section explicitly left "whether the gate should
  still act on an expired claim's conflict" as a question for this milestone to answer. The answer
  this milestone gives is **no** — the plan's own M4 scope line names exactly two inputs ("alone"),
  and `ttl` is not one of them. Introducing a THIRD staleness concept (claim-ttl-expiry, alongside
  checkpoint freshness) with no stated bound, no stated relationship to `STALENESS_BOUND_MS`, and no
  named consumer of the distinction, would be exactly the kind of guess `0001-contracts.md` Decision 3
  and this account's own standing note (`speculative-flexibility-costs-rounds.md`) warn against making
  before a real need proves it out. This remains an open question for M5/M7, now answered for M4
  specifically rather than silently inherited.
- **`claim.mode`** — nothing in plan §2's `Intervention` refusal list or §4 M4's own refusal list
  conditions any intervention's availability on read/write/exclusive mode.
- **`checkpoint.resumable`** — plan §2 conditions how honestly the checkpoint-anchored halt mode must
  be DESCRIBED once selected ("declared, honestly, as best-effort-resumable, not guaranteed") on this
  field, never whether it is AVAILABLE — `availableInterventions` only answers the latter question.
  `checkpoint.checkpointId` is likewise unread here for the same reason: this function never
  constructs an `Intervention`, so it never needs a `checkpointId` to populate one.

## Decision 5 — `lib/gate/clock.ts`: the first Timestamp arithmetic in this codebase, and why the staleness bound is a disclosed policy constant, not a guessed invariant

`lib/contracts/timestamp.ts`'s own header explicitly defers instant-parsing to "the code that actually
needs [it] to compute freshness/staleness against a bound (M3's `detectConflicts`, M4's
`availableInterventions`)." M3 never needed it (`0003-detection.md` Decision 4: `detectConflicts` reads
no timestamp at all). This milestone is the first to actually parse one. `clock.ts`'s
`isCheckpointFresh` fails closed on every axis it cannot verify — unreachable, unparseable `declaredAt`/
`now`, or a future-dated `declaredAt` (clock skew) all resolve to "not fresh," never to "fresh" — the
same "cannot order, treat as the least permissive/most stale case" discipline
`.genesis/decisions/0003-detection.md` already states for a different comparison (claim timestamps) and
plan §5's own failure-suite case 7 states for a heartbeat, both re-derived here independently for a
checkpoint rather than imported.

`STALENESS_BOUND_MS` (5 minutes) is exported as a named, disclosed policy constant, not hidden inline
or invented as a hard-coded literal duplicated between the implementation and its tests. No frozen
contract or plan text names a numeric bound anywhere — this is an unavoidable, un-evidenced policy
choice this milestone had to make for "fresher than a configured staleness bound" to mean anything at
all, stated as exactly that in `clock.ts`'s own header rather than presented as a researched or
justified number it is not.

**Alternative considered and rejected: add a fifth parameter (`stalenessBoundMs`) to `availableInterventions`
so a caller can configure it.** Rejected — the plan's own M4 scope line names exactly four parameters;
adding a fifth not asked for anywhere is the same unrequested-flexibility shape this account's own
standing note warns against, and no milestone in this plan has a stated need to vary the bound per call.

## Decision 6 — the source-scan story, corrected after L4 VERIFY rejected this decision's first version: a text scan alone is NOT sufficient; a second, checker-based check closes the gap the text scan cannot; a third, narrower residual remains disclosed

**This decision was revised after L4 VERIFY (independent review) rejected the version of it first
opened, having found and reproduced two working routes past `__tests__/architecture.test.ts`'s own text
scan, neither being identifier aliasing nor the `fromCharCode`/concatenation limit that scan already
disclosed.** The original version of this decision argued that a plain text scan was *sufficient* for
this milestone's own falsifiability check, because the specific attack that forced `human-id.test.ts`
onto the real compiler (import aliasing) has no analogue for a bare string literal's own spelling. That
argument is correct as far as it goes — **and it does not go far enough**, because it treats "not
vulnerable to aliasing" as "sufficient," when a third mechanism, distinct from both aliasing and runtime
string assembly, also reaches the forbidden literal with no matching source text for a text scan to find.

**Route 1 — type computation, reported as ordinary, idiomatic TypeScript, not an attack:**

```ts
import type { Intervention } from "../contracts/intervention.js";
type HaltVariant = Extract<Intervention, { kind: "halt" }>;
export type HiddenHaltMode = HaltVariant["mode"];   // includes the human-authorized literal
```

This compiles clean in `lib/gate/`, contains **zero occurrences** of the forbidden literal anywhere in
its source text, and `architecture.test.ts` reported 7/7 passing against it. Independently confirmed via
an `extends`-probe that `HiddenHaltMode` really does include the human-authorized mode's own literal as
a member. This is neither aliasing (no identifier's spelling diverges from what it resolves to — there
is no cast, and no import is renamed) nor runtime string assembly (there is no runtime value at all here,
only a type-level computation) — it is a **third, independent mechanism**: `Extract`, an indexed access,
a conditional type, or a mapped type can all resolve a *named* type to include a literal that never
appears, spelled, anywhere in the type's own declaration.

**Route 2 — a generic-helper cast, the same shape `human-id.ts`'s own header already names for the
brand, reported alongside Route 1 but NOT a new class:**

```ts
function unsafeCast<T>(x: unknown): T { return x as T; }
function leak(x: Extract<Intervention, { kind: "halt" }>): AvailableInterventionKind {
  return unsafeCast<AvailableInterventionKind>(x.mode);
}
```

This is the identical shape `human-id.ts`'s own header already names and discloses as "route B" for
`HumanId` — a generic instantiated at its own call site, with the target type named only as a type
ARGUMENT, never inside a cast expression or a type annotation anywhere. It belongs to the same
open-ended, unenumerable class (`any`, a generic instantiated at its call site, `JSON.parse`, and
whatever a future reviewer invents next) this account already ruled, once, not worth chasing further —
see Decision 2 of `.genesis/decisions/0001-contracts.md` round 3. **This decision does not change that
ruling for Route 2.** It is disclosed, with a real passing test confirming it is not caught (see below),
not silently rediscovered.

**Why Route 1 is different from Route 2, and from `human-id.ts`'s own routes A/B, and why that
difference changes what this project owes here:** every previously-disclosed residual in this codebase
(`HumanId`'s routes A/B, `architecture.test.ts`'s own runtime-string-assembly limit) shares one property:
the question "did this happen" is **not decidable** by any fixed scan, because the underlying class is
open-ended (every value of type `any`; every possible way to assemble a six-character string at runtime).
Route 1 is not open-ended. "Does this type annotation's *resolved* type include the specific string-
literal type this project cares about" is a single, well-defined question the real type checker can
answer exactly, every time, for any type expression whatsoever — `Extract`, indexed access, conditional
types, mapped types, or any future TypeScript feature computing over `Intervention`. A scan built on
top of the checker's own resolved type, not on source text, closes this **specific, named, decidable**
question completely, the same way `human-id.test.ts`'s checker-based symbol resolution closed the
aliasing question completely once it stopped chasing text. This is why the coordinator's own M1 ruling
("do not extend the scanner again") does not transfer here without qualification: that ruling was scoped
to an *unenumerable* class (any route from a raw value to a branded type); this is a *decidable* one, and
treating every "the scanner missed something" report as automatically belonging to the unenumerable
class would have been an even worse failure than the original, overclaiming text-scan argument.

**Chosen: build the closed, checker-based check.** `__tests__/type-leak.test.ts` reuses
`human-id.test.ts`'s own scaffolding (one `API` instance per test file, `Node#forEachChild` walking,
fail-closed on `getSyntacticDiagnostics`, a fresh `API` per scratch-file analysis) and asks a different
question of the checker: for every type-annotation-bearing position this milestone's own non-test source
can write (`TypeAliasDeclaration`, `VariableDeclaration`, `PropertyDeclaration`/`PropertySignature`,
`ParameterDeclaration`, `IndexSignatureDeclaration`, or a function/method/arrow function's own return
type), resolve the annotation's type via `Checker.getTypeFromTypeNode` and recurse through unions
(`isUnionType`/`getTypes()`) checking each member for being the exact string-literal type
(`isStringLiteralType`/`.value`) this project's `Intervention["mode"]` union uses for its highest-risk
member. This catches Route 1 exactly (confirmed: the reported `HiddenHaltMode` example is caught, with
its own source text confirmed to never spell the forbidden literal) and two structural variants of it
(the same computation inline as a function's return type with no separate alias; the same computation
reached via a variable's own annotation) — see that file's own "EXPLOIT REGRESSION" tests. It does
**not**, and is not claimed to, catch Route 2 — that file's own "DISCLOSED LIMIT" describe block
reproduces Route 2 verbatim and confirms, with a real passing assertion, that it is not caught, the same
discipline `human-id.test.ts` already uses for its own honest residuals.

**⬇ BEGIN RETRACTED SPAN — SUPERSEDED BY ROUND 4, FAR BELOW. THIS FENCE ENCLOSES EVERY PARAGRAPH DOWN TO
THE EXPLICIT "⬆ END RETRACTED SPAN" MARKER, NOT JUST THE ONE IMMEDIATELY BELOW IT — an earlier version of
this marker said "this paragraph" (singular) and a completeness-sounding claim survived two paragraphs
later, undetected by that narrower fence; this is the fix, named so a reader does not have to guess where
the boundary falls a second time. Both paragraphs inside this span originally argued the question "does a
type in `lib/gate/**` resolve to the forbidden literal" was *decidable* in the sense of being *closeable in
one mechanism*, and that a checker-based scan over resolved types would close the *entire* class of
type-computation indirection (below: "closes the *entire* class... in one mechanism", and again "the
type-level gap Route 1 named was real and now closed by `type-leak.test.ts`"). Three further rounds of
independent review each found a real declaration position the resulting scan missed — round 4's own
finding is that the CATEGORY of "positions a declaration-walking scan must enumerate correctly" is, in
practice, exactly as easy to under-enumerate as the text-scan positions round 2 walked, even though the
underlying compiler QUESTION (what type did the checker assign here) is decidable for any one position
asked about. "Decidable per position" does not imply "the set of positions worth asking is enumerable
without error" — that conflation is this span's own mistake, corrected in ROUND 4 below, which demotes
this whole check from a completeness claim to a best-effort recall layer. Both paragraphs are preserved,
unedited, as the record of what was believed at the time, per this account's own standing rule against
rewriting history — they are superseded, not deleted. (A fourth finding, also after this span, is recorded
in ROUND 4 as well: an array/tuple type, e.g. `Extract<Intervention,{kind:"halt"}>["mode"][]`, evades
`typeContainsForbiddenLiteral`'s union-only recursion — see ROUND 4's own closing paragraph.)**

**The argument for building this check at all, rather than only disclosing Route 1 more prominently, per
the coordinator's explicit invitation to make the call and defend it either way:** the case *against* is
real — a second checker-based scan is a second mechanism to maintain, and this project's own account-wide
practice (`speculative-flexibility-costs-rounds.md`) generally favors fewer moving parts. The case *for*
wins here because (1) the question is decidable, not an arms race — there is no "next Route 1.5" the way
there was always a "next Route C" for `HumanId` chasing file extensions; a checker-based scan over
resolved types closes the *entire* class of type-computation indirection in one mechanism, not one
example at a time; (2) this codebase already pays the fixed cost of depending on
`typescript/unstable/sync`/`typescript/unstable/ast` for exactly this class of check, so the marginal
cost of a second, differently-scoped scan reusing the same scaffolding is small; (3) Route 1's own
plausibility is the deciding fact the coordinator named directly — an engineer extracting a named type
alias for reuse is completely ordinary, unlike a deliberately adversarial cast, so a gap here is far more
likely to be hit by accident than `HumanId`'s disclosed routes ever were.

**What actually excludes the human-authorized halt mode, restated at its true strength now that the
text scan's own claim has been corrected:** the load-bearing guarantee remains
`AvailableInterventionKind`'s own `Exclude<>`-derived definition (Decision 1) — there is no member, no
field, no code path in `available-interventions.ts` that can PRODUCE a value naming that mode. A second,
independent fact reinforces this, worth stating explicitly because the coordinator asked for it directly:
`availableInterventions`'s own signature — `(agent: AgentId, claim: ResourceClaim, checkpoint:
CheckpointDeclaration, now: Timestamp)` — has **no parameter of type `Intervention`, or of any type that
structurally contains one**, so even a `HiddenHaltMode`-style type alias sitting inert in this package
has no live `Intervention` value anywhere in this module's own runtime to leak through it: the type-level
gap Route 1 named was real and now closed by `type-leak.test.ts`, but it was never a *value*-level leak
in this module's actual data flow, because no `Intervention` value flows into or through this module at
all. `architecture.test.ts`'s plain text scan is now correctly understood as a third, narrower,
REDUNDANT layer — it still catches every case where the literal is spelled directly, and remains useful
for exactly that subset, but is no longer described anywhere in this codebase as sufficient on its own.

**⬆ END RETRACTED SPAN.** Everything from "⬇ BEGIN RETRACTED SPAN" above through this line is superseded by
ROUND 4, below — read that subsection for the corrected claim. What remains true and is NOT retracted,
restated independently in ROUND 4 itself so it does not depend on this span at all:
`AvailableInterventionKind`'s own closed `Exclude<>` definition (Decision 1), and
`availableInterventions`'s signature carrying no `Intervention`-typed parameter, are the load-bearing
guarantee — that specific claim was correct when first written above and remains correct now; only the
claim that a scan "closes" or has "closed" the type-computation class around it is retracted.

**The honest limit, disclosed rather than chased, now stated for both remaining scans together:** neither
`architecture.test.ts`'s text scan nor `type-leak.test.ts`'s checker-based scan catches Route 2 (a generic
cast naming the target type only as a type argument at its own call site) or runtime string assembly —
both disclosed, with real passing tests, as the same open-ended, unenumerable class `human-id.ts`'s own
routes A/B already name, not chased further here for the identical reason it was not chased there.

**Made case-insensitive, deliberately beyond the plan's own literal-case quoted text (`architecture.
test.ts` only):** an exact-case scan would let a trivial re-capitalization slip past on a technicality
that defends nothing real — the same "closes today's known spelling, leaves an adjacent one open" shape
this project elsewhere refuses to call a genuine closure.

**A real constraint this decision places on this milestone's own prose, stated honestly:** because
`architecture.test.ts` matches the substring case-insensitively and anywhere (not just as a whole word),
this milestone's own non-test source under `lib/gate/**` cannot use the word "enforced" (which contains

`available-interventions.ts`'s own header used the identifier name of a `lib/contracts` export

**ROUND 3 — L4 VERIFY confirmed round 2's fix (the reported route plus five structural variants it tried
independently: a conditional type, an interface property, a namespace-nested alias, a parameter position,
and `satisfies`) as "real engineering, not decoration," then reported two further routes round 2's
ANNOTATION-POSITION enumeration cannot see:**

```ts
// 1 — inferred types, no annotation anywhere
function getMode(x: Extract<Intervention, { kind: "halt" }>) { return x.mode; }
export const modeValue = ({} as Extract<Intervention, { kind: "halt" }>).mode;

// 2 — a generic type parameter's own default, never visited
export type Container<T = Extract<Intervention, { kind: "halt" }>["mode"]> = { value: T };
```

Both independently proved to carry the forbidden literal (`tsc --declaration --emitDeclarationOnly` for
the first; a non-vacuous `extends` probe for the second) while round 2's scan reported 12/12, zero leaks,
against both. **The defect was the enumeration strategy itself, not the two missing positions**: round 2
walked AST nodes with an explicit `.type` field and asked what each resolved to — an inferred return type,
an inferred `const`, and a type parameter's `defaultType` field are three more type-bearing positions
`typeAnnotationOf` never listed, and patching those three in would only invite a fourth, the same shape of
mistake this account has already paid for on `human-id.test.ts` (four rounds) and a sibling project's own
architecture test (five rounds on one function).

**The fix, per the coordinator's own explicit instruction: iterate DECLARATIONS, not syntax forms, and ask
the checker for the type it actually ASSIGNED to each one, regardless of how (or whether) that type was
written.** `type-leak.test.ts` was rewritten to resolve, per declaration kind, via the semantic API that
gives the real, checked type independent of annotation:

- Value-shaped declarations (`VariableDeclaration`, `Parameter`, `PropertyDeclaration`/`PropertySignature`,
  a destructured `BindingElement`) — `checker.getSymbolAtLocation(name)` then
  `checker.getTypeOfSymbol(symbol)`, the identical call whether annotated or inferred. Closes the
  `modeValue` gap by construction: there is no separate "or it's inferred" branch to omit.
- Callable declarations (`FunctionDeclaration`, `ArrowFunction`, `FunctionExpression`,
  `MethodDeclaration`/`MethodSignature`, a get/set accessor) — `checker.getSignatureFromDeclaration(node)`
  then `checker.getReturnTypeOfSignature(signature)`, again identical whether the return type is annotated
  or inferred. Closes the `getMode` gap the same way.
- `TypeAliasDeclaration` — `checker.getSymbolAtLocation(name)` then `checker.getDeclaredTypeOfSymbol(symbol)`
  (never the missing case, since a type alias always has an explicit `.type`, but rewritten through the
  same symbol-based pattern for consistency rather than reading `.type` directly, which was round 2's own
  narrower and now-abandoned approach).
- `TypeParameterDeclaration.defaultType` — the one deliberate, NAMED exception, exactly as the coordinator
  instructed: a type parameter's own declared/symbol type does not expose its default's resolved type at
  all (a default only ever gets instantiated at a use site omitting the argument, which this file does not
  attempt to enumerate), so `checker.getTypeFromTypeNode(node.defaultType)` is resolved directly, named
  explicitly as the single remaining syntactic-node resolution in this file rather than silently folded
  into the "iterate declarations" story as if it were the same kind of case.

**Why this is the last enumeration, not a third one, argued rather than merely asserted:** every case above
is keyed to a DECLARATION KIND — a small, fixed, language-defined set (there is no way to declare a value,
a callable, or a type in TypeScript outside this list) — never to whether that declaration happens to carry
a `.type` node, which was round 2's actual axis of failure. A future TypeScript feature can add a new way
to WRITE a type (`satisfies` and `as const` already exist today and are both covered, because neither
changes what declaration KIND the enclosing binding is), but it cannot add a new declaration KIND without
this file needing a new node-kind guard for the identical reason `human-id.test.ts` needs one for each new
AST shape TypeScript adds — an enumeration over the compiler's own fixed DECLARATION grammar, not over the
open-ended space of type EXPRESSIONS a declaration's type might be written or computed from. This is
exactly the distinction the coordinator drew explicitly between this check (decidable, closeable) and
`HumanId`'s routes A/B (unenumerable, correctly left open).

**Verified, not merely re-asserted:** all three round-2 exploit-regression cases (the original
`HiddenHaltMode` alias, the inline-return-type variant, the variable-annotation variant) plus the two new
round-3 cases (`getMode`'s inferred return, `modeValue`'s inferred const) plus the type-parameter-default
case are all caught by the rewritten file — 19/19 tests passing, including new false-positive-discipline
tests (an ordinary function with an ordinary inferred return type; a type parameter default resolving only
to the checkpoint-anchored mode's own literal; a destructured binding element with an unrelated inferred
type) proving the rewrite did not trade precision for recall.

**Route 2 (the generic-cast-at-call-site route reported alongside route 1 in round 2) remains disclosed,
not chased, and this round does not revisit that ruling** — L4 VERIFY itself called that distinction "the
right distinction in principle" and "consistent, not convenient." A generic-helper cast naming its target
type only as a type argument at its own call site has no DECLARATION whose assigned type this file's
new, declaration-based enumeration could inspect to see it either — the cast expression itself is not a
declaration, and the generic function's own declared return type is its type parameter, not this project's
literal. Still pinned with a real, passing `toEqual([])` assertion, per L4 VERIFY's own confirmation that
this specific test "would fail loudly if that route ever started being caught rather than passing either
way."

**The smaller correction requested alongside the main one: the "fails closed" claim was stated more
broadly than it holds.** The scan's fail-closed path is `getSyntacticDiagnostics` only — a file with an
unresolvable import (`TS2307`, a semantic error, not a syntax one) parses fine and is scanned normally.
L4 VERIFY judged this not itself a leaking route (an unresolved reference resolves to the checker's error

broader than the actual guarantee. `type-leak.test.ts`'s header now states precisely what it fails closed
on (a syntax error only) and why extending to every semantic diagnostic would be the wrong fix (an
unrelated type error anywhere in the file would silently stop this specific check from running at all,
which is a worse failure mode than the narrow, named gap being replaced) — with a new test confirming a
file with a real semantic error but no syntax error still scans normally, rather than being refused.

**ROUND 4 — L4 VERIFY rejected round 3 a third time, with a ruling that ends this loop rather than
starting a fourth round of the same shape.** The coordinator's own words, recorded here because they are
the actual disposition of this check, not paraphrased into something weaker: "I have twice said 'last

```ts
class HasPrivate  { #mode:      Extract<Intervention,{kind:"halt"}>["mode"] = ... }  // private field

```

All three compiled clean with zero literal occurrences, and round 3's scan reported 19/19, zero leaks,
against all three.

**The two category errors, named plainly, exactly as the coordinator diagnosed them, because a future
reader should not have to reconstruct why this file's own resolution logic looks the way it does:**

1. **Round 2's error:** gated on *whether a node had an explicit `.type` field* — an inferred function
   return, an inferred `const`, and a type parameter's `defaultType` were all invisible to it because none
   of them carried that field.
2. **Round 3's error, a NARROWER FORM OF THE SAME MISTAKE:** round 3 correctly stopped reading `.type` and
   started resolving each declaration's own checker-assigned type — but, before doing so for a value
   declaration, it gated on `isIdentifier(node.name)`, so a `ComputedPropertyName` or a `PrivateIdentifier`
   was skipped even though the ENCLOSING declaration kind (`PropertyDeclaration`) was already in round 3's
   own enumerated kind list. Separately, and with no relation to the identifier gate at all,
   `TypeParameterDeclaration.constraint` and `.defaultType` are sibling, independent `TypeNode` fields on
   the identical node — round 3 visited only `defaultType`, with no stated reason for excluding
   `constraint`. Both are instances of the same underlying pattern: a plausible-looking condition
   (`isIdentifier`, "the field named in the coordinator's example") narrower than the actual scope of what
   round 3's own kind list already claimed to cover.

**The fix, mechanical and bounded, exactly as instructed:** `node.name` is now passed to
`checker.getSymbolAtLocation` directly, for whatever kind of name node it is — no `isIdentifier` gate, no
new name-kind-specific branch, just removing the condition that was narrower than the enclosing check
already promised. `TypeParameterDeclaration.constraint` is now resolved alongside `.defaultType`, the same
way, for the same reason: they are two instances of one field kind (a type parameter's own auxiliary type
node), not two separate features one of which needed a bespoke justification to add.

**The claim, demoted from completeness to recall — the part of this round that actually matters, per the
coordinator's own framing, quoted here rather than restated in different words because restating it would
risk drifting from what was actually decided:**

> This is a best-effort recall layer. It resolves the checker's assigned type for the declaration kinds it
> enumerates, and that enumeration is not proven complete — three rounds of adversarial review found a
> missed position each time, and there is no reason to believe the next round would not. The load-bearing
> guarantee is elsewhere: `AvailableInterventionKind`'s closed `Exclude<>` definition, and
> `availableInterventions`'s signature carrying no `Intervention`-typed parameter, so a stray type-level
> position in this package has no live value to carry.

`type-leak.test.ts`'s own header, `available-interventions.ts`'s header, and `architecture.test.ts`'s
header were all rewritten to state this, with every prior phrasing implying position-independence,
entire-class closure, or "the last enumeration" removed — not narrowed further, REMOVED, because a
completeness claim over TypeScript's declaration surface is falsified by one counterexample and this
milestone produced one per round, from a different direction each round, while a recall claim is true as
stated and STAYS true when the next position is found: the next finding would improve the check rather
than falsify this document.

**Why this is the correct resting state, and not a fourth enumeration attempt:** per the coordinator's own
explicit instruction, this round does not attempt a fourth completeness claim. A genuinely complete
approach was considered — iterating the module's symbol table directly (`checker.getExportsOfModule`/a

**What survived independent review across all rounds, so a future reader does not re-litigate it:** the
