# ADR 0006 — M6 domain: three concurrent incident-remediation agents, and the two gaps M4/M5's own ADRs left for this milestone to close

- **Date:** 2026-09-22
- **Status:** accepted
- **Phase / milestone:** M6 (INTEGRATE) — `domains/incident-response/**`, `scripts/demo-incident.ts`

## Context

`.genesis/PLAN.md` §4 M6's own scope: "three autonomous remediation agents (`AutoScaler`, `RollbackBot`, `CacheFlusher`) responding to one production incident, each claiming exclusive or shared control of overlapping services, heartbeating progress and checkpoint state, wired end to end through M3→M4→M5." `lib/contracts`, `lib/conflict`, `lib/gate`, and `lib/arbitrate` are frozen and out of scope — this milestone treats them strictly as inputs (`git diff main -- lib` stays empty). Its own falsifiability check: `npm run demo:incident` runs a realistic scenario and prints, per step, the claims in force, the detected conflict, the gate's permitted set, and the final ruling, with all five `Intervention` top-level kinds and both `halt` modes appearing at least once — checked by the script's own exit code.

Two things became clear while actually wiring the frozen engine to a realistic scenario, neither invented for this milestone but both real, previously-undocumented gaps in the plan and in M1–M5's own ADRs:

## Decision 1 — `computeSeverity` and blast radius: a function the plan names but no milestone ever builds

`lib/contracts/conflict-severity.ts`'s own header states `ConflictSeverity` is "computed from the conflicting resource's declared blast radius and the conflict kind... never asserted directly by an agent about itself," but `grep -rn "computeSeverity\|blast radius" lib/` (run before writing this ADR) returns only that one header comment — no implementation anywhere in `lib/`. This is the identical "the plan names a concept it never fixes a shape for" pattern already closed, once each, by `Heartbeat` (`lib/conflict/heartbeat.ts`, M3) and `HumanAuthorization` (`lib/arbitrate/human-authorization.ts`, M5): owned by the first milestone with a real consumer, not retrofitted into a frozen directory.

**Shape chosen** (`domains/incident-response/service-catalog.ts` + `severity-policy.ts`): a disclosed, five-entry `SERVICE_CATALOG` mapping each scenario resource to a `BlastRadius` (`"small" | "medium" | "large"`), and `computeSeverity(kind, blastRadius)` mapping `small/medium/large → benign/contained/corrupting` as a baseline, with exactly one adjustment: `undeclared-access` is bumped one severity step above whatever the same blast radius would give a declared (`write-write`/`write-read`) conflict, capped at `corrupting`. This directly satisfies plan §2's own refusal for that kind — "refuses to be treated as any weaker than the other two" — as a checked property (`__tests__/severity-policy.test.ts`), not merely an example. `write-write` and `write-read` are deliberately never distinguished from each other: the plan draws no severity distinction between them, and inventing one would be exactly the unrequested flexibility this account's own standing note (`speculative-flexibility-costs-rounds.md`) warns against.

No numeric evidence backs the base mapping or the one-step bump — the identical, honestly-disclosed limitation `lib/gate/clock.ts`'s `STALENESS_BOUND_MS` and `lib/arbitrate/severity-ladder.ts`'s `SEVERITY_MINIMUM_RUNG` already carry for their own invented policy constants.

## Decision 2 — combining multiple agents' evidence into the single `available` set `arbitrate` expects: a gap that fell through M4 and M5 both

`lib/gate/available-interventions.ts`'s own header states its scope is evaluated "against exactly one claim" and explicitly defers the harder question: "See `.genesis/decisions/0004-gate.md` for why closing the multi-claim ('every claim's') half of that [quarantine] sentence is left to M5, not guessed at here." Reading `0004-gate.md` and then `lib/arbitrate/arbitrate.ts` directly (not assuming the deferral was honored) shows it was not: `arbitrate`'s own signature takes `available: readonly AvailableInterventionSet[]`, one ALREADY-COMPUTED set per conflict, as an INPUT from its own caller — it contains no call to `availableInterventions` anywhere and no code that combines several claims' worth of it. The gap named as "left to M5" was never actually closed there; it fell through, unclosed, all the way down to whichever milestone first has multiple real claims per conflict to combine. M3's own fixtures never model this (`lib/conflict/__tests__/fixtures.ts` builds claims and checks conflicts, never a combined gate result); M4's and M5's own test suites always hand-construct `available` directly (`availableSet(...)` in `lib/arbitrate/__tests__/fixtures.ts`). This milestone is the first with a real, multi-agent conflict to test the answer against — this is a genuine plan defect, named here rather than silently resolved, in the tradition of M3's `Heartbeat` gap, M4's two contradictions, and M5's per-conflict severity defect.

**The two readings, and why the more conservative one was chosen:** plan §2's own quarantine text — "refuses to fire when every revoked claim's corroboration is self-reported" — admits two readings for a multi-agent conflict: **(a)** offer quarantine for the conflict as a whole once *at least one* participant's claim clears `self-reported` (a per-claim OR/union), or **(b)** offer it only once *every* relevant participant's own evidence would independently support it (an AND/intersection). Reading (a) is dangerous given what `lib/arbitrate/arbitrate.ts`'s own `claimIdsOf` actually does once quarantine is offered: it revokes every relevant participant's claim indiscriminately, not filtered by that specific participant's own corroboration — so (a) would let one well-corroborated agent's evidence license revoking a *different* agent's still-self-reported claim, precisely the "disbelieve a self-report and act on that disbelief anyway" failure this project's whole thesis exists to refuse. Reading (b) — chosen — is the same fail-closed shape every other ambiguous axis in this codebase already resolves (checkpoint freshness, claim-timestamp disagreement, authorization-conflict mismatch — see `gate-aggregation.ts`'s own header for the full citation chain). **Intersection, not union**, for both axes this milestone's gate combination touches (`quarantine`'s corroboration floor and `pause`/`halt-checkpointed`'s checkpoint freshness).

**Falsifiability, proved, not merely argued:** `domains/incident-response/__tests__/gate-aggregation.test.ts` constructs asymmetric fixtures directly (one participant self-reported, the other independently-verified; one fresh checkpoint, one stale) and asserts the conservative reading wins. The scenario itself (`scenario.ts`) was deliberately built with one genuinely asymmetric conflict — `checkout-service`'s two claims (RollbackBot self-reported, AutoScaler cross-checked) — specifically so this policy is demo-visible, not only unit-tested: an earlier draft of this scenario had every conflict's participants share identical evidence, which would have let a union-vs-intersection regression pass `npm run demo:incident` silently. As a live experiment (see this milestone's own build report), flipping `combinedAvailableInterventions`'s intersection to a union: (1) fails 7 tests across `gate-aggregation.test.ts` and `end-to-end.test.ts`, and (2) makes `npm run demo:incident` itself exit 1 on a real, load-bearing assertion (`checkout-service`'s gate wrongly grants `quarantine`) — reverting restores byte-identical demo output and a fully green suite.

## Decision 3 — `undeclared-access` has no `ResourceClaim` at all: how the domain still asks the frozen gate a real question

`availableInterventions`'s signature (`lib/gate/available-interventions.ts`, frozen) requires an actual `ResourceClaim` object as its third parameter; `undeclared-access` is, by plan §2's own definition, exactly the case where no such claim exists for the offending agent on the resource it touched. Fabricating one would be dishonest (the tower would be asserting a claim the agent never made). Instead, `gate-aggregation.ts`'s `noLegitimateClaimEvidence` passes a claim whose own `agentId` is a documented sentinel (`NO_LEGITIMATE_CLAIM_AGENT`), provably different from the agent under discussion — this exercises `availableInterventions`'s own documented consistency guard ("when `claim.agentId !== agent`, this function fails closed to the baseline ONLY") for precisely the reason that guard exists: there is no report from that agent on this resource at all. `__tests__/gate-aggregation.test.ts` proves the sentinel's own `mode`/`ttl`/`corroboration` fields are inert — only the identity mismatch drives the result — so this is not a hidden dependency on unremarked-upon field values. No `ArbitrationParticipant` is supplied for an `undeclared-access` conflict either, for the identical reason: there is no legitimate claim or checkpoint to cite, and `arbitrate`'s own `uniqueCheckpointId`/`claimIdsOf` already fail closed to `null` on an empty participant list, which is the honest answer.

## The scenario, and why it is shaped this way

Five conflicts across five cataloged services, chosen to exercise refusals, not a happy path:

1. **`checkout-service`** (write-write, `large` → `corrupting`): asymmetric corroboration (Decision 2's demo-visible case) plus a fresh, shared checkpoint. Gate withholds `quarantine`; severity demands it; arbitration falls back to `halt`/`checkpointed` with `escalationRecommended: true` — then, re-run with a human authorization scoped to this exact conflict, fires `halt`/`forced` instead. A third re-run, with an authorization scoped to a *different* conflict, proves the mismatch is refused (identical ruling to the no-auth run). This is the plan's own "riskiest design decision," demonstrated as a live contrast, not asserted in prose.
2. **`session-cache`** (write-read, `medium` → `contained`): both cross-checked, neither has a usable checkpoint — the gate withholds `pause`/`halt-checkpointed` on staleness/absence, and `quarantine` (the only realizable option that meets the floor) fires, proving proportionality holds even when the sufficient option happens to be the strongest one on offer.
3. **`feature-flag-config`** (write-write, `medium` → `contained`): the *same* conflict evaluated twice, five minutes apart — before a checkpoint exists (falls back to `warn`, escalation recommended) and after one appears (now meets the floor with `pause`, not the also-available-but-stronger `halt-checkpointed`) — a second, independent "what changes when the evidence improves" contrast.
4. **`internal-metrics-store`** (write-write, `small` → `benign`): deliberately unremarkable evidence; `observe` is already adequate and nothing escalates it.
5. **`diagnostic-log-bucket`** (`undeclared-access`, bumped to `contained`): no legitimate claim exists; the gate can only offer the baseline; arbitration falls back to `warn` with escalation recommended — proving the "never weaker" refusal for real, including through a resource cataloged as `small`.

Across these, all five `Intervention` top-level kinds and both `halt` modes are selected at least once (`__tests__/end-to-end.test.ts`'s own coverage test, and `scripts/demo-incident.ts`'s own final summary assertion) — the plan's own M6 falsifiability check, satisfied by the script's exit code, not eyeballed.

## Decision 4 — the honest shape of this milestone's guarantees, recorded after L4 VERIFY went past its own brief

L4 VERIFY approved this milestone as sound, not merely clear — three things belong in this committed record rather than only in that review, because an unstated exemption or an unstated cost is how a later reader concludes a guarantee is broader, or an engine property cheaper, than it actually is.

**4a. Why `domains/` is deliberately exempt from `lib/`'s architecture scans — not just left unresolved.** `lib/contracts/intervention.ts`'s own header, under "THE TWO HONEST RESIDUALS, NAMED TOGETHER, PLAINLY," states the second residual verbatim: "A CALLER of this library, OUTSIDE `lib/` entirely, forging an authorization and passing it in as a parameter — out of scope for every milestone this plan names, and correctly so." `domains/` is exactly that caller. Every real `HumanAuthorization` this codebase can ever construct — including this milestone's own demo/test fixtures (`"ops-lead-jordan" as HumanId`) and, eventually, whatever M8's real human-facing boundary produces — has to be assembled *outside* `lib/`, because `lib/` deliberately mints no `HumanId` anywhere (`human-id.ts`'s own header: no minting function exists, by design). If `lib/`'s no-minting/no-self-construction guarantee were extended to cover `domains/` as well — by widening `import-containment.test.ts`'s `LIB_ROOT` or adding a parallel scan over `domains/` — it would forbid the one legitimate act this design exists to permit: a caller, outside the engine, constructing a real authorization and handing it to `arbitrate()` as that function's own documented input. The scan's boundary is `lib/` specifically because `lib/` is the party that must never manufacture authorization on its own initiative; `domains/` is the party that must be free to supply one. This is not an oversight left for a future milestone — it is the same boundary M1 already drew, restated here so it does not have to be re-derived by whoever reads this ADR next.

**4b. What the guarantee does not, and structurally cannot, prevent — demonstrated, not merely disclosed.** L4 VERIFY's own scratch test, outside this milestone's brief, wrote a file under `domains/incident-response/` that constructed a `HaltForced` value by hand — `{ kind: "halt", mode: "forced", authorizedBy: "nobody-really-authorized-this" as HumanId, conflictId: "..." as ConflictId }` — entirely bypassing `arbitrate()`. It typechecked and ran, and printing it would show a fabricated forced halt with no real authorization behind it at all. **This contradicts no claim this codebase makes**: `.genesis/decisions/0001-contracts.md` Decision 2 and `intervention.ts`'s own header both scope the "no module ever mints a `HumanId` or assembles this variant from scratch" guarantee to modules *under `lib/`* — never to a caller of the library — and `human-authorization.ts`'s own header already discloses that `lib/` "cannot confirm `authorizedBy` names a real, consenting human." The verifier confirmed this milestone's own code never does this: every `Intervention` this codebase prints comes off a real `ruling.intervention` returned by a real `arbitrate()` call, traced through `scripts/demo-incident.ts`'s own `assertRuling`. But the honest shape of the guarantee is worth stating plainly rather than leaving a reader to discover it independently: **the safety of `halt`/`forced` rests on `domains/` and app code *choosing* to route every intervention through `arbitrate()`'s gated `humanAuthorization` parameter — not on anything `lib/` structurally prevents a caller from doing once outside its own boundary.** A future domain or app milestone that constructs an `Intervention` literal directly, anywhere outside `lib/`, is making the identical choice this scratch file made; nothing in this codebase's architecture prevents it, by design, because preventing it would require constraining code `lib/` does not and should not own.

**4c. The placement cost of `gate-aggregation.ts`'s intersection policy.** Decision 2's intersection-over-union choice was judged correct on the merits, confirmed against real `arbitrate.ts` behavior (`claimIdsOf` revokes every relevant participant's claim once quarantine is offered, with no per-participant corroboration filter, so a union really would let one agent's evidence license revoking another's still-self-reported claim) — and `lib/gate` is frozen, so `domains/` was the only compliant place this policy could live at all. The consequence is worth naming rather than leaving implicit: **a load-bearing safety policy now lives outside the engine**, protected by this milestone's own ordinary unit tests (`__tests__/gate-aggregation.test.ts`) rather than by `lib/gate`'s architecture-scan-backed guarantees (the same class of proof `available-interventions.ts`'s own type-level exclusion and `architecture.test.ts`'s source scan give the single-claim case). Any future domain built on top of `lib/gate` — one this project does not build — would have to reinvent this exact reasoning from scratch; `lib/gate` itself gives it no help, because the multi-claim question was never actually its job (Decision 2). Noted here for M9's own documentation to carry forward, not treated as a defect to fix in this milestone.

## What was NOT done, disclosed rather than silently decided

- **No priority-based preemption, no automatic dispossession** — consistent with the plan's own "considered and rejected" list; this milestone's scenario does not attempt to resolve the `checkout-service` collision automatically, by design.
