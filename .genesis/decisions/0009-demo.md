# ADR 0009 — M8 the interactive demo: what the browser is allowed to change, why it is scoped to one conflict, and how it stays incapable of throwing

- **Date:** 2026-09-22
- **Status:** accepted
- **Phase / milestone:** M8 (BUILD) — `app/**`, `components/**`

## Context

`.genesis/PLAN.md` §4 M8's own scope: "the M6 incident scenario, live: a clean run (no conflict,
`observe` throughout) and an 'inject a colliding remediation' run (conflict detected, gate computed
live on screen, ruling fires with its cited rule and evidence) — both driving the real engine, never
UI-scripted." Its own refusal: "to render a ruling the engine didn't actually produce for the exact
inputs on screen at that moment (no pre-baked transcript)." The milestone's own task brief adds a
concrete floor beyond the plan's prose: the viewer must be able to weaken/strengthen a conflict's
corroboration, make a checkpoint stale/fresh, and supply/withhold a human authorization, and see the
gate's permitted set and the arbitrated ruling update — and names the exact headline moment this
project's whole thesis rests on: refuse to force-halt on the tower's own evidence, force-halt once
given an authorization scoped to that exact conflict, refuse again for an authorization scoped to a
different one. `lib/**`, `domains/**`, and `tests/failures/**` are frozen; this milestone can only add
`app/**`/`components/**` code that calls the existing, frozen engine — never edit what it calls.

## Decision 1 — one pure bridge function owns every engine call; the component never calls the engine itself

`components/demo/compute-demo-view.ts` exports `computeDemoView(knobs: DemoKnobs): DemoResult`, a
plain function with no React import at all. It is the *only* file under `components/demo/` that
imports `detectConflicts`, `combinedAvailableInterventions`, or `arbitrate`. `IncidentDemo.tsx` calls
it once, directly in its render body, and renders exactly what comes back — it has no code path that
constructs an `Intervention`-shaped value, a ruling, or an available-set on its own. This is the
concrete mechanism behind "everything rendered must come from the real engine": a code reviewer can
confirm it by checking one file's import list, not by tracing every JSX branch in the component for a
hand-written string that happens to look like a ruling.

`compute-demo-view.ts` returns a typed result, `{ ok: true; view: DemoView } | { ok: false; error:
string }` — the same discipline `lib/conflict/detection-result.ts`'s `DetectionResult` already uses,
independently re-derived for this milestone's own bridge rather than imported (this file is not
`lib/`, and importing a `lib/` pattern by *shape* is not the same as importing `lib/` code, which stays
untouched). See Decision 4 for why this exists and what it actually guards against.

## Decision 2 — no derived state, no effects: the sibling-project trap named directly in this milestone's own brief

This milestone's task brief names a specific failure mode by name: a sibling project's M8 "had a
stale-state race predicted by its own failure suite: components holding derived state that drifts from
the source," found safe only because "the components had no `useEffect`, `useCallback`, `setTimeout`
or `async` anywhere." `IncidentDemo.tsx` follows the identical discipline, independently re-verified
for this codebase: it holds exactly one `useState` (`knobs`, the four levers — `injected`,
`rollbackCorroboration`, `checkpoint`, `authorization`), and computes `computeDemoView(knobs)` fresh on
every render. There is no second state slot holding a *copy* of `available`/`ruling`/`checkoutConflict`
that could disagree with what the current knobs would produce; the values on screen this render are
always the values `computeDemoView` returned for the knobs on screen this render, because they are the
same call. `grep -rn "useEffect\|useCallback\|useMemo\|setTimeout\|async " components/` returns nothing
in this milestone's own source (test files use `async` only where `vitest`'s own API requires it, e.g.
none does here — every test in this milestone is synchronous). This holds precisely because the engine
underneath (`lib/`) is itself synchronous and pure, per this account's own house style — this milestone
did not need to argue for the safety of an async boundary because it introduced none.

## Decision 3 — the interactive knobs are scoped to one conflict (checkout-service), not all five

The plan's own scenario (M6) detects five conflicts across five resources. This milestone's UI exposes
live knobs over exactly one of them — `checkout-service` — while still running the real,
un-narrowed `CLAIMS`/`HEARTBEATS` underneath so the other four conflicts are still genuinely detected
(used for `otherConflictId`, see below) and not deleted from the scenario, only left off this UI's own
control surface.

**Why this one:** `.genesis/decisions/0006-domain.md`'s own scenario design calls `checkout-service`
"the scenario's central 'gate ceiling' moment," and this milestone's own task brief names its exact
three-part story as "the headline moment": refuse-then-force-then-refuse-again over the identical
conflict, driven only by whether a human authorization is present and whether it is scoped correctly.
No other conflict in this scenario exercises all three human-authorization states meaningfully — the
authorization branch in `arbitrate` only ever fires when `meetingFloor` is empty (see
`lib/arbitrate/arbitrate.ts`), which for `session-cache`/`feature-flag-config`/`internal-metrics-store`
either isn't true at the severity these already demonstrate, or is true for reasons (missing checkpoint
alone) already covered by `checkout-service`'s own checkpoint knob. Building a human-authorization
control that would visibly do nothing for four of five conflicts would be a knob that lies about its
own effect — worse than not offering it.

**What this leaves out, disclosed rather than silently narrowed:** a viewer cannot interactively
re-shape `session-cache`, `feature-flag-config`, `internal-metrics-store`, or `diagnostic-log-bucket`'s
own evidence from this page. Their real, engine-computed rulings are not shown on this page at all —
only `session-cache`'s conflict id is surfaced, and only as the concrete "different conflict" value the
authorization knob's third option cites (a real, live-detected id, not a fabricated placeholder
string). `npm run demo:incident` remains the only place all five conflicts and all five `Intervention`
kinds appear in one run; this UI's own honest claim is narrower — one conflict, fully interactive,
matching the plan's own singular "headline moment" language rather than promising five.

## Decision 4 — defense in depth against `combinedAvailableInterventions`/`arbitrate` throwing, and why it is a *second* layer, not the first

Both frozen functions this milestone calls can throw: `combinedAvailableInterventions` throws when its
`evidence` array doesn't cover `conflictParticipants` exactly (missing or extra agents);
`arbitrate` throws on a `conflicts`/`available`/`severities` length mismatch or a duplicate conflict id
within one call.

**The primary guarantee is structural, not defensive.** `compute-demo-view.ts` only ever calls
`arbitrate` with single-element arrays (`[checkoutConflict]`, `[available]`, `[severity]`) built from
the same `checkoutConflict` value in the same call — a duplicate-id or length-mismatch is not
reachable, because there is only ever one conflict in the call at all. `combinedAvailableInterventions`
is only ever called with an `evidence` array built from exactly `checkoutConflict.agentIds` (RollbackBot
and AutoScaler, read off the same real `DetectedConflict` the evidence is being built to describe) —
there is no code path where `DemoKnobs` can name a third agent, drop one of the two, or duplicate one;
`buildClaims`'s own `flatMap` either keeps or drops AutoScaler's single claim based on one boolean, and
always keeps RollbackBot's. This was checked directly, not merely argued: `__tests__/
compute-demo-view.test.ts`'s first test enumerates the full `DemoKnobs` cross-product (2 × 3 × 3 × 3 =
54 states) and asserts `result.ok === true` for every one — a real exhaustive check over every state
this UI's own controls can reach, not a sample.

**The second layer is `computeDemoView`'s own `try`/`catch`,** wrapping every engine call and returning
`{ ok: false, error }` instead of letting an exception escape. This exists for the case the first layer
is a *claim*, not a proof past this milestone's own git history: a future edit to this file (or to a
knob's own UI, adding a fifth choice without updating `buildClaims`) could reintroduce exactly the
class of bug the exhaustive test above currently rules out. When that catch fires, `IncidentDemo.tsx`
renders a distinct, visible error panel (`role="alert"`, red border, the caught message, and a reset
button) instead of a blank page — checked directly by sabotaging `compute-demo-view.ts` during this
milestone's own build (dropping AutoScaler's evidence entry, reproducing the exact
`combinedAvailableInterventions` throw this decision describes) and confirming both effects: the
targeted exhaustive test failed with a real, informative assertion diff, and — separately — the catch
converts what would otherwise be an uncaught exception into the typed failure branch. The sabotage was
reverted before this ADR was written; it is not part of the shipped diff.

**Answering the milestone's own question directly: can this UI construct an input that throws?** No,
by construction, for every state its controls can reach (proven exhaustively, not sampled). The
`try`/`catch` exists anyway, and is real, tested defense-in-depth — not a first line, because a
first line that is *only* a catch block would let a broken engine call recompute a subtly wrong
`DemoView` silently as long as it happened not to throw; the exhaustive construction-level proof is
what actually backs the "never wrong for the knobs on screen" claim, not the catch.

## Decision 5 — what "gate's permitted set" and "arbitrated ruling" render as, verbatim vs. formatted

`view.available` (from `combinedAvailableInterventions`) is rendered as its own sorted member list,
unmodified — no prose summary is substituted for it. `view.ruling` (from `arbitrate`) is rendered
through `format-intervention.ts`, a second pure, engine-import-free module: `formatInterventionHeadline`
and `formatInterventionDetail` switch exhaustively on `ruling.intervention.kind` (and `.mode` for
`halt`) via the same `assertNeverIntervention` guard `scripts/demo-incident.ts`'s own
`describeIntervention` uses, independently re-derived here (not imported — `scripts/**` is not
`components/**`) so a future sixth `Intervention` variant fails this file's own typecheck exactly the
way it already fails `scripts/demo-incident.ts`'s. Every other field on `InterventionRuling`
(`rule`, `escalationRecommended`, and all four fields of `evidence`) is rendered directly, by name, with
no paraphrase — a viewer (or a verifier comparing this page against `npm run demo:incident`'s own
printed output for the identical conflict) can check every rendered value against the real
`InterventionRuling` shape `lib/arbitrate/intervention-ruling.ts` defines.

## What this milestone leaves open, honestly

- **No browser-automation test simulates an actual click.** `vitest.config.ts` stays `environment:
  "node"` (no jsdom) so `lib/`'s own framework-free test environment is untouched by this milestone;
  `IncidentDemo.render.test.tsx` instead renders the component via `react-dom/server`'s
  `renderToStaticMarkup` against a range of *initial* knob states (added via an `initialKnobs` prop, for
  exactly this purpose) — proving the component renders the right markup for a given state, not that a
  click transitions between two states inside a running browser. That gap is closed by
  `compute-demo-view.test.ts` instead: it calls the identical pure function every `onClick`/`onChange`
  handler calls via `setKnobs`, so the state-transition logic itself is tested directly, just not
  through a simulated DOM event. A human (or a browser-driving tool) checking the deployed URL directly
  remains the only check of the actual click-to-re-render path; this milestone's own build report
  records exactly that check being performed against the deployed page, not merely against local
  intentions.
- **Four of five scenario conflicts are not interactively controllable from this page** — see Decision
  3. Their real rulings exist (`npm run demo:incident` prints all five), but only `session-cache`'s
  conflict id surfaces on this page, and only as a value, not as its own interactive panel.
- **The staleness boundary itself (N vs. N+1 milliseconds) is not re-demonstrated by this UI's
  checkpoint knob** — it offers "stale" as 12 minutes past the 5-minute bound, a comfortable margin
  that demonstrates the flip without re-litigating the exact boundary, which already has its own
  dedicated, frozen test (`lib/gate/__tests__/clock.test.ts`). Reproducing the exact-boundary case in
  the UI would need a fifth checkpoint option whose only purpose is re-proving a fact M4 already
  proves; this milestone judged that not worth the added control-surface complexity.
