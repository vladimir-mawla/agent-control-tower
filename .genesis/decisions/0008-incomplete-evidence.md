# ADR 0008 — a real defect in merged code: `combinedAvailableInterventions` never checked evidence coverage, so incomplete input produced a MORE permissive result

- **Date:** 2026-09-22
- **Status:** accepted
- **Phase / milestone:** post-M7 bug fix (`main` at M7 done, 7 of 9) — `domains/incident-response/gate-aggregation.ts` and its call sites, plus this file. Not a milestone; `lib/**` is untouched (`git diff main -- lib` stays empty — see Verification in the PR description).

## Context

Adversarial verification against the merged M6 domain found a live defect in `domains/incident-response/gate-aggregation.ts`'s `combinedAvailableInterventions`: it never checked that its `evidence` array covers every participant of the conflict it is being asked to evaluate. Because the function intersects one `AvailableInterventionSet` per evidence entry, dropping a participant's entry makes the intersection run over **fewer** sets — structurally, intersecting over a subset of the real inputs can only ever produce a result that is a **superset** of (or equal to) the correct one. Incomplete input therefore cannot make the result more restrictive; it can only make it more permissive, which is exactly backwards for a function whose entire documented purpose (ADR 0006 Decision 2) is to fail closed.

**Reproduced, live, before any fix:** with both `checkout-service` agents' real evidence, the combined set is `{observe, warn}` (quarantine correctly withheld — RollbackBot's own claim is still self-reported). With RollbackBot's evidence entry simply omitted from the array — the shape a caller that only gathers evidence for agents that heartbeated this cycle would produce by accident, not a hostile or contrived input — the combined set becomes `{observe, warn, quarantine}`. Feeding that into `arbitrate` alongside **both** real participants fires a full-confidence `quarantine` (`rule: "severity-satisfied"`, `escalationRecommended: false`), revoking both agents' claims, including RollbackBot's own still-self-reported one. This is precisely the "disbelieve a self-report and act on that disbelief anyway" outcome ADR 0006 Decision 2's intersection policy exists to prevent — reached through the **correct** combinator (the real, frozen `availableInterventions`, the real intersection loop) called on **incomplete** input, not through a wrong combinator. That second failure mode — a hand-built union standing in for the real function — is the separate, already-pinned `tests/failures/10-intersection-policy-unenforced-by-lib.test.ts` (M7). This defect is new and distinct: the right function, fed a silently short array.

The empty-evidence case (`evidence.length === 0` returning the unconditional `{observe, warn}` baseline) was already correct and stays correct — it is a disclosed fallback for "no relevant participant at all," argued in the function's own original header as structurally safe (`{observe, warn}` costs nothing even when technically ungranted, the identical reasoning `arbitrate.ts`'s own `observe` fallback uses). The defect is specifically a genuinely incomplete **non-empty** array: some but not all participants' evidence present.

## Decision 1 — fail closed by requiring the conflict's participant set as an explicit parameter, never inferred from `evidence` itself

`combinedAvailableInterventions` now takes a new, required second parameter, `conflictParticipants: readonly AgentId[]` — the conflict's own full, authoritative participant set (in practice, `DetectedConflict.agentIds`, which every real call site already has in hand before calling this function). The function validates, before doing anything else:

1. No duplicate agent id within `conflictParticipants` itself.
2. No duplicate agent id within `evidence` itself.
3. The set of agent ids named by `evidence` equals `conflictParticipants` exactly — no participant missing an entry, no entry naming an agent outside the conflict.

Any violation throws, with a message naming exactly which agents are missing or extraneous.

**Why a parameter, not a heuristic inferred from `evidence`:** this account's own standing note (`speculative-flexibility-costs-rounds.md`) and this project's own repeated experience (`.genesis/decisions/0005-arbitration.md` Decision 1, `0006-domain.md` Decision 2) are that building machinery to tolerate or infer around a malformed input costs more, later, than requiring the caller to hand over the canonical shape up front. There is no way to derive "the conflict's real participant set" FROM `evidence` that would not simply re-derive whatever incomplete set `evidence` itself already has — the missing participant's absence from `evidence` is the exact fact being checked, so deriving the expected set from `evidence` would make the check blind to its own failure mode by construction. The only source of truth for "who is actually party to this conflict" that exists anywhere in this codebase is `DetectedConflict.agentIds` (`lib/conflict/detected-conflict.ts`, frozen) or an equivalent a caller builds by hand for the same purpose — so that is what this function now demands as an explicit argument, exactly as the brief for this fix required.

## Decision 2 — throwing, not a refusal return value, and why `domains/` being the boundary makes the case for throwing stronger, not weaker

**The chosen behavior: throw a plain `Error`.** Two live precedents in this codebase, both close analogues, were weighed against each other:

- `lib/arbitrate/arbitrate.ts` (frozen, M5) **throws** on a duplicate conflict id and on an `conflicts`/`available`/`severities` length mismatch — both described in that file's own header as "input-validation throws for in-batch shape violations that are checkable from data already in hand," i.e. an internal consistency check between two or more values the SAME caller assembled, not a judgment call about ambiguous or adversarial external data. ADR 0005 frames this as the right shape specifically because the violation is a caller bug, not a legitimate outcome any well-behaved caller would ever need to express and recover from at the type level.
- `lib/conflict/detect-conflicts.ts` (frozen, M3) instead returns a typed `DetectionResult` (`{ ok: true, conflicts } | { ok: false, error }`) for **hostile external input** — a throwing getter, a `Proxy` that throws on iteration — arriving at the one real boundary of this whole system where the caller is not this codebase's own trusted composition but whatever untrusted process hands claims/heartbeats to `detectConflicts`. Plan §4 M3's own brief specifically calls for "a typed failure result, never an uncaught exception" for exactly that reason: a hostile input crashing the tower is itself an availability problem worth designing around.

`combinedAvailableInterventions`'s two inputs — `evidence` and `conflictParticipants` — are not analogous to `detectConflicts`'s boundary. Both are always assembled, in every real call site this codebase has, by the SAME domain-layer code from the SAME `DetectedConflict` (see `scripts/demo-incident.ts` and `domains/incident-response/__tests__/end-to-end.test.ts`, both updated by this fix to pass `conflict.agentIds` straight from the `DetectedConflict` already in scope). A coverage mismatch between them is not a message arriving from outside this system that this system must survive; it is two values, minted by the caller's own aggregation code, disagreeing with each other — the identical shape `arbitrate`'s length-mismatch and duplicate-id checks already throw on, not the identical shape `detectConflicts`'s hostile-input guard returns a value for.

**Being in `domains/` rather than `lib/` makes throwing the *more* appropriate choice here, not less — argued, not assumed:**

1. ADR 0006 Decision 4a already establishes that `domains/` is deliberately the party responsible for assembling correct, real inputs to hand to the frozen engine — "a CALLER of this library, OUTSIDE `lib/` entirely... is exactly that caller," free to do the composition `lib/` itself is forbidden from doing. Assembling a complete, coverage-correct `evidence` array for a real conflict is squarely inside that responsibility. A coverage gap here is `domains/`'s own aggregation bug — not a foreign input this layer exists to buffer the rest of the system against, the way `detectConflicts` must buffer against a hostile external claims array.
2. `lib/` cannot return an ergonomic refusal value for every possible caller misuse without inventing a `Result`-shaped return type for what is, definitionally, a programming error rather than a legitimate business outcome — exactly the "machinery to tolerate malformed input" this codebase has already paid for twice (Decision 1 above). `domains/` is not `lib/`: it has no obligation to stay maximally generic against every conceivable caller, and a `Result`-typed refusal here would only add a discriminated union every downstream caller (`scripts/demo-incident.ts`, every test) would need to unwrap for a condition that, on the actual evidence of this codebase's real call sites, should never legitimately occur — every real caller already has the conflict's true participant set sitting in scope before it calls this function.
3. The asymmetry in cost of being wrong argues the same way. A refusal value silently threaded through — if a future caller failed to check it — degrades to exactly this defect's own failure mode: a plausible-looking `AvailableInterventionSet` reaching `arbitrate` with a hole in it, `arbitrate` unable to tell the difference (this is `tests/failures/10`'s own finding, restated). A thrown exception cannot be silently ignored the same way; it stops the caller's whole aggregation step immediately, at the exact point the incomplete input was assembled, during development and in production alike — loud failure over a safety-critical path being strictly preferable to a quiet one revoking a real agent's claim on partial evidence.

**Honest limit of this argument:** throwing does mean a caller who does not wrap this call in its own error handling will crash rather than degrade gracefully. This project accepts that trade explicitly, matching `arbitrate`'s own precedent, rather than inventing a softer failure mode for a condition this codebase's own real call sites should never actually trigger.

## Decision 3 — where the new test proving this lives, and why

The task brief drew a bright line: a test that merely proves the system now works correctly is a regression test and belongs in `domains/incident-response/__tests__/`, not `tests/failures/**` (M7's own, frozen, twelve-case suite, each one required to name a real REMAINING limit).

**Split accordingly:**

- `domains/incident-response/__tests__/gate-aggregation.test.ts` gained the defect-reproduction test (first proven red against the old two-argument signature, then updated to pin the fixed, throwing behavior — see the PR description's transcript) plus two supporting tests (an extraneous evidence entry is refused the same way; a duplicate `conflictParticipants` entry is refused, distinctly). These prove the fix works. They are regression tests for a real, previously-merged defect, and belong beside this file's own existing unit tests — not in the frozen failure suite, which is not the venue for "the bug is now fixed."
- `tests/failures/13-coverage-check-trusts-its-own-participants-parameter.test.ts` (new, added after M7, not editing any of M7's own twelve cases or `0007-failure-suite.md`) pins the honest REMAINING limit this fix does not close: `combinedAvailableInterventions` can only check that `evidence` and `conflictParticipants` agree with EACH OTHER — it has no way to verify that `conflictParticipants` itself is the conflict's real, full participant set, because it is never handed a `DetectedConflict` to check against, only whatever array the caller supplies. A caller whose own upstream aggregation derives BOTH arrays from the same incomplete source (e.g. filtering to "only agents that heartbeated this cycle" once, then reusing that filtered list for both arguments) reproduces the exact live defect this ADR fixes, with no exception at all, because the two arguments still agree with each other. This is a genuine, falsifiable, currently-true limit of the shipped fix, not a hypothetical caveat — the test proves it by constructing exactly that caller shape and showing `arbitrate` still fires an unwarranted, full-confidence `quarantine`.

## Decision 4 — what this fix does and does not close, stated plainly

**Closes:** the specific, reproduced defect — `combinedAvailableInterventions` given a non-empty `evidence` array missing one or more of its OWN stated `conflictParticipants` (or naming an agent outside them) now throws instead of silently returning a set computed over fewer participants than intended. Every real call site in this codebase (the M6 demo scenario, the M6/M7 test suites) has been updated to supply the conflict's real `agentIds`, and all of them continue to pass with byte-identical `npm run demo:incident` output — the fix is pure input validation added around already-correct behavior for well-formed input; it changes no ruling this codebase's own real scenario ever produces.

**Does NOT close:** the whole class of "incomplete evidence" problems, for two disclosed reasons argued above:

1. It validates internal agreement between two caller-supplied arguments, not agreement between either argument and ground truth (`detectConflicts`'s real output) — see Decision 3's discussion of `tests/failures/13`.
2. It is scoped to `combinedAvailableInterventions` specifically. Nothing about this fix constrains a future caller from constructing an `AvailableInterventionSet` some other way entirely (hand-rolled, a union, or otherwise) and handing it to `arbitrate` directly — that is `tests/failures/10`'s own, separate, already-disclosed limit (ADR 0006 Decision 4c: the intersection policy is "a load-bearing safety policy [that] now lives outside the engine," a `domains/`-owned convention, not a `lib/`-enforced guarantee), unchanged by this fix.

This fix closes exactly the coverage gap it was written to close, demonstrated by a failing-then-passing test and a load-bearing revert-and-restore (see the PR description). It is not, and does not claim to be, a closure of every way `combinedAvailableInterventions` or its callers could still be fed a wrong `AvailableInterventionSet`.
